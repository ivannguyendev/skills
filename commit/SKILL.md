# Conventional Commits

Follow these conventions when creating commits.

## Prerequisites

Before running Git commands, check if the agent has been granted permissions for the specific commands used in this workflow: `git branch`, `git status`, `git diff`, `git add`, `git commit`, and `git push`. If not, use the `ask_permission` tool with `Action: "command"` for each required target (e.g., Target: "git status", Target: "git diff", etc.) to obtain authorization. This limits permissions strictly to what is needed.

Before committing, always check the current branch:

```bash
git branch --show-current
```

**If you're on `main` or `master`, stop and ask the user to create a feature branch first** — unless the user explicitly asked to commit to main. Do not auto-create a branch. The user (or their preferred tool/skill) must produce the branch; you only verify.

After the user creates the branch, re-check:

```bash
git branch --show-current
```

If still on `main` or `master`, stop — do not commit.

## Required Format

```
<type>(<scope>): <short description>

- <bullet point 1 describing completed work>
- <bullet point 2 describing completed work>
```

- **`<type>(<scope>): <short description>`** — header (required). Type from the table below. Scope optional. Description in imperative mood, no trailing period, max 70 chars.
- **Body** — A blank line followed by a bulleted list describing what was done. Expand on what/why. User provides it, or AI suggests and asks the user to confirm.

## Workflow

1. Run `git status` and `git diff --staged` (and `git diff` for unstaged) to understand the changes.
2. Pick the appropriate `<type>` from the table below.
3. Draft the `<short description>` — propose one based on the diff.
4. Draft the bullet points for the body detailing the tasks completed.
5. Let the user accept or replace the proposed commit message.
6. Build the message with the exact format above and commit using a HEREDOC.
7. Determine if the user's initial prompt explicitly requested to push (e.g. "push", "commit and push", "commit rồi push", or similar). If yes, perform the push directly. Otherwise, proceed to Post-Commit Follow-up.

## Commit Types

| Type     | Purpose                           |
| -------- | --------------------------------- |
| `feat`   | New feature                       |
| `fix`    | Bug fix                           |
| `ref`    | Refactoring (no behavior change)  |
| `perf`   | Performance improvement           |
| `docs`   | Documentation only                |
| `test`   | Test additions or corrections     |
| `build`  | Build system or dependencies      |
| `ci`     | CI configuration                  |
| `chore`  | Maintenance tasks                 |
| `style`  | Code formatting (no logic change) |
| `update` | Small content/value update        |

## Description Rules

- Header description: Imperative, present tense: "Add feature" not "Added feature"
- No period at the end of the header
- Maximum 70 characters for the header
- The body must be a bulleted list (using `- `) explaining **what** was done and **why**, not how

## AI-Generated Changes

Do **not** add any AI attribution to commit messages — no `Co-Authored-By: Claude`, no "Generated by AI", no "🤖 Generated with Claude Code", no "Written with Claude", no in-body markers. Commits must read as if written by the developer, regardless of how the changes were produced.

## Examples

### Bug fix

```
fix(api): Handle null response in user endpoint

- Add null check before accessing user properties to prevent dashboard crash
- Update unit tests for null user scenario
```

### Feature

```
feat(alerts): Add Slack thread replies for alert updates

- Post a reply to the original Slack thread when an alert is updated or resolved
- Keep related notifications grouped instead of creating new messages
```

### Small update

```
update(seens): Adjust id format for seens payload

- Align seen record id with the PowerSync schema
- Allow downstream consumers to dedupe correctly
```

## Committing With the Exact Format

Always pass the message through a HEREDOC so the indented body lines survive shell quoting:

```bash
git add . && git commit -m "$(cat <<'EOF'
fix(api): Handle null response in user endpoint

- Add null check before accessing user properties to prevent dashboard crash
- Update unit tests for null user scenario
EOF
)"
```

## Post-Commit Follow-up

After a successful commit, determine if the user explicitly requested pushing in their instruction (e.g., they said "push", "commit and push", "commit rồi push", or similar).

- **If push was explicitly requested**:
  1. Proceed to push directly without asking.
- **If push was NOT explicitly requested**:
  1. Ask the user a single yes/no question, naming the branch explicitly. Example: _"Push this commit to `origin/<branch>`?"_
  2. Only proceed if the user confirms.

1. Confirm the commit succeeded (`git status` shows a clean working tree or only unrelated changes).
2. Capture the current branch name:

   ```bash
   git branch --show-current
   ```

3. Perform the push:
   - If the branch already tracks a remote: `git push`
   - If no upstream is set yet: `git push -u origin <branch>`

If the user declines the push prompt, stop — do not push and do not ask again in the same turn.

**Never push to `main` or `master`** without an explicit instruction from the user that names the branch. Never use `--force` / `--force-with-lease` unless the user asks for it.

After pushing, report the result (success, or the error message verbatim if it failed) so the user can act on it. If successful, always construct and provide a clickable remote link to the commit (e.g., `https://github.com/<owner>/<repo>/commit/<hash>`) so the user can easily view it in their browser.

## Principles

- Each commit is a single, stable change
- Commits should be independently reviewable
- The repository should be in a working state after each commit
- Pushing is never automatic — always confirm with the user first (unless explicitly pre-authorized in the user's initial prompt)
